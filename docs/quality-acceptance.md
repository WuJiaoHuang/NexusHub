# 代码质量验收与可靠性边界

## 权限规则

全局拦截顺序为 Token 刷新、登录检查、管理员授权。取消对 `/events/**`、`/places/**` 和历史上传接口的整段匿名放行。

匿名入口通过具体 HandlerMethod 的 `@PublicEndpoint` 显式标注，仅包括现有地点/活动只读方法、地点分类、热门动态、验证码与登录。报名及个人报名状态均要求登录。规则不依赖原始 URL 字符串比较，尾斜杠或矩阵参数不会使管理方法变为公开方法。

地点新增/更新、活动创建、地点索引重建及历史图片删除标注 `@AdminOnly`。需要用户已通过服务器端 Redis Token 认证，且用户 ID 在 `nexushub.security.admin-user-ids`（环境变量 `ADMIN_USER_IDS`，逗号分隔）中。默认空值拒绝全部管理操作。管理员白名单由运维配置，不接受请求 JSON、Header 或个人资料中的角色声明。匿名返回 401，已登录但未授权返回 403；原 REST URL、请求字段和业务响应结构不变。

当前验证码入口仍是开发实现：直接返回模拟验证码，没有真实短信验证手机号所有权。管理员白名单依赖可信认证，不能将这个开发登录流程直接用作生产管理员认证。本次遵守不修改现有认证 API 契约的范围，未新增短信服务或改写认证架构。

## 消费者与事务

`tryLock` 返回 false 时抛出异常；`InterruptedException` 分支恢复中断标志并抛出异常。异常继续从消费者传播，进入现有重试、拒收、死信与补偿流程，不将尚未写入数据库的消息当作消费成功。

插入记录与数据库条件扣减仍在同一事务中；唯一索引、容量条件、正常重复消息的幂等处理和锁维度不变。锁仍在方法内部释放，事务由代理提交，最终并发保护依赖数据库唯一索引及条件更新。

## 发送结果与补偿

启用 Spring AMQP 2.2 的关联 publisher confirms、publisher returns 和 RabbitTemplate mandatory。使用 registrationId 关联发送结果，默认最多等待 5000 毫秒，由 `REGISTRATION_PUBLISH_CONFIRM_TIMEOUT_MS` 配置。

| 结果 | 行为 |
| --- | --- |
| broker ack 且没有退回消息 | 返回原有受理成功结果，仍需查询最终报名状态 |
| mandatory 无路由退回 | 调用既有 Lua 补偿，成功后返回失败与可重试提示 |
| broker 产生的 nack（无框架原因） | 补偿预占名额并返回失败 |
| 建立发布连接失败或序列化失败 | 发布前失败，执行幂等补偿并返回失败 |
| 确认超时、I/O 异常、带框架原因的 nack 或中断 | 可能已送达，保留预占，返回待确认提示并记录关联 ID |
| 明确未投递但补偿失败/没有确认返回值 | 返回名额恢复待处理，记录错误，不能宣称名额已恢复 |

框架可能在连接关闭时产生 nack，不能把它与明确的 broker 拒绝混为一谈。返回消息与关联确认的行为依据当前版本的 [Spring AMQP 2.2 参考文档](https://docs.spring.io/spring-amqp/docs/2.2.x/reference/html/)。

既有补偿标记 `event:registration:compensated:{registrationId}`、86400 秒 TTL、所有 Redis Key、两份 Lua 和 RabbitMQ 拓扑名称不变。补偿服务只接受 Lua 返回的 0（本次补偿）或 1（已补偿）；其他结果抛出异常，消费者不会静默将其当作成功。

## 旧消息兼容

转换器显式将旧 `com.campuslink.dto.EventRegistrationMessage` 类型头映射至当前消息类，只接受这个历史入站别名；不需要加载旧包。即使没有监听方法的推断类型也能读取历史消息。新消息继续发出 `com.nexushub.dto.EventRegistrationMessage` 类型头，不回写旧品牌类型。其他旧 Java 类不在信任范围内。

Exchange、Queue、Routing Key 的既有名称保持兼容。迁移 SQL 中的旧表名是迁移来源，不是运行时残留。

## 运维核对与未覆盖窗口

本次没有引入 Outbox 或跨 Redis/MQ/MySQL 分布式事务，不宣称恰好一次或消息绝对可靠。以下情况需要结合日志中的 registrationId、eventId、userId 核对：

- Redis 预占后进程在发送前崩溃。
- 确认丢失或超时、连接中断等导致投递结果不确定。
- Redis 故障导致发送侧补偿或死信补偿失败；死信队列的有限重试耗尽后没有第二级持久化失败队列，需要监控错误日志、broker 拒收及人工处置。
- 补偿标记过期后的历史消息回放，或者存在在途报名时重启预热。

核对前暂停相关活动的新报名，等待消费者与在途消息稳定，检查数据库报名记录、主队列/死信队列和 Redis 预占。已有记录或消息仍在队列/处理中时，不得直接增加名额。只有证实没有落库且不会再被消费时，才在受控运维环境使用相同 registrationId 调用既有幂等补偿，并保存审计记录。不能只凭 HTTP 失败响应或数据库暂时没有记录就补偿。
